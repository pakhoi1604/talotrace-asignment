# Phase 2: Schema, migration, config

## Overview
Add 5 nullable result columns to `scoring_jobs` (enforced in the ORM), create `hr_sessions` and `score_decisions`, add HR settings. One autogenerated migration on top of `7e042563977a`.

## Requirements
- Functional: append-only decisions with DB-enforced ordering; hashed sessions with expiry; job results that can't show a failed job as a score.
- Non-functional: autogenerate only (AGENTS.md rule 1); never edit `7e042563977a`; named constraints; `alembic check` clean.

## Architecture

```
answers 1─1 scoring_jobs (+ result columns)
answers 1─* score_decisions   (newest sequence counts)
hr_sessions                   (standalone; email is the HR identity)
```

### `scoring_jobs` result columns (added by this plan's migration)
| Column | Type |
|---|---|
| `suggested_score` | int null |
| `suggested_reason` | Text null |
| `needs_person_reason` | Text null |
| `model` | str(100) null |
| `finished_at` | dt null |

**Invariants: ORM-enforced, not DB CHECKs.** Alembic autogenerate doesn't emit CHECKs for an existing table, and hand-written migrations are banned (user decision 2026-11-02). Enforcement in `app/models/scoring_job.py`:
- `@validates("suggested_score")`: `None` or 1–4, else `ValueError`.
- `event.listen(Session, "before_flush")` (registered once in `app/models/scoring_job.py`) runs `job.check_result_invariants()` for each new or dirty `ScoringJob`:
  - `status == scored` → `suggested_score` and `suggested_reason` not null
  - `status in (queued, running, failed)` → `suggested_score is None`. **A failed job never carries a score**
  - `status == needs_person` → `needs_person_reason` not null
  - `superseded` → no rule (keeps whatever it had)
- Raises `ValueError("scoring job <id>: <rule>")`.
- The rules live in a module-level `validate_job_result(status, suggested_score, suggested_reason, needs_person_reason)`, and `check_result_invariants` calls it. The worker plan (`261102-1549-llm-scoring-worker`) reuses it to validate outcomes before its fenced bulk UPDATE, so there is one rule set.
- Bulk `UPDATE` statements skip ORM events. `retry_job` (phase 5) clears the score columns in the same statement. The worker writes results with conditional UPDATEs (`WHERE status='running'`) whose values were validated by `validate_job_result` first, and it writes every score column on each outcome. Recorded in architecture.md.

Do **not** also declare `CheckConstraint`s for these on the model. Tests build the schema with `create_all`, so they would enforce CHECKs that migrated DBs lack. Tests would pass while production behaves differently. Keep one enforcement path.

### New tables
| Table | Columns | Constraints |
|---|---|---|
| `hr_sessions` | `id` int PK, `token_hash` str(64), `email` str(255) (canonical `HR_EMAIL`), `credential_fingerprint` str(64), `created_at`, `expires_at` | UNIQUE(token_hash), INDEX(expires_at) |
| `score_decisions` | `id` int PK, `answer_id` FK→answers, `sequence` int, `kind` str(10), `score` int, `reason` Text null, `hr_email` str(255), `created_at` | UNIQUE(answer_id, sequence); CHECK kind IN ('override','accept'); CHECK score BETWEEN 1 AND 4; CHECK kind <> 'override' OR reason IS NOT NULL |

New tables get real DB CHECKs (autogenerate renders them inside `create_table`).
- `DecisionKind` StrEnum (`override`, `accept`) in `app/models/enums.py`.
- `Answer.decisions` relationship ordered by `ScoreDecision.sequence.desc()`.
- `sequence` = previous max + 1 per answer. The unique pair makes concurrent writers collide instead of both inserting.

### Config (`app/core/config.py`)
```python
HR_EMAIL: str | None = None
HR_PASSWORD: str | None = None
HR_SESSION_TTL_HOURS: int = 12
HR_COOKIE_SECURE: bool = False   # True behind HTTPS
```
`field_validator("HR_EMAIL", "HR_PASSWORD", mode="before")`: blank or whitespace-only → `None`, so `HR_PASSWORD=` in `.env` means "not configured" (503), not an empty password. <!-- Red Team: tests read dev .env / blank creds -->
`credential_fingerprint` lets phase 3 revoke every session when the `.env` account changes.
`.env.example`: `HR_EMAIL=hr@example.com`, `HR_PASSWORD=hr-demo-password` with comment `# MOCK sign-in: the only HR account. Change for any shared setup.`

## Risk Assessment
- No DB guarantee for job invariants: raw SQL or bulk updates can bypass them. Mitigated by one bulk-update site (retry, which clears scores) and the worker contract in architecture.md. The read side (phase 4) also hides `suggested_score` for any job not `scored`/`needs_person` (`visible_suggestion`), so a bad row can never surface as a score.
- `before_flush` listener registered on the global `Session` class applies to every session, including tests. Intended.
- Existing local `.env` files lack HR vars → sign-in returns 503 with a clear message. README tells the user to copy the vars from `.env.example`.
