# HR review API

Source brief: `V2_Full_Stack_Engineer_Take_Home_Brief.pdf` ("HR area", "What must be true"). UI reference: `docs/design/hr *` mockups (sign-in, candidates per role, candidate review).
Builds on `261102-1509-candidate-api-db-seed` (models, token auth, 422 handler, `make seed`). That plan must land first.

## Goal
HR signs in (mock, single `.env` account), lists roles and candidates, reads every answer with its job status, suggested score and reason, sees which submission counts, overrides (reason required) or accepts a suggestion, retries failed jobs, lists jobs by status, and plays audio answers. **Backend only. No LLM worker, no frontend.** Suggested scores are written by the later worker plan. This plan only defines the result columns and reads them.

## Decisions (locked with user, 2026-11-02)
| Area | Decision |
|---|---|
| Sign-in | **One HR account from `.env`** (`HR_EMAIL`, `HR_PASSWORD`). Anything else → 401. Labelled **MOCK sign-in** in docs. Anyone (a candidate too) can reach the sign-in endpoint, but only that account succeeds |
| Session | Random token, sha256 stored in `hr_sessions` (expiry `HR_SESSION_TTL_HOURS`=12, checked in SQL). Sent as an httpOnly `hr_session` cookie, `SameSite=Lax`, `Path=/`. Sign-out deletes the row. A credential fingerprint revokes all sessions when the `.env` account changes or is unset. HR auth reads **only** the cookie and ignores `Authorization`, so a candidate Bearer token can never open an HR route |
| CSRF | HR `POST`s require `Content-Type: application/json` (415 otherwise). Retry takes `{}`. With no CORS middleware, cross-origin JSON fails preflight. SameSite alone is not relied on |
| Accept | Only on a `scored` job whose suggestion equals the posted score. `needs_person` → 409: HR must override with a reason (user decision, red team) |
| Demo password | `.env.example` ships `HR_PASSWORD=hr-demo-password`, live after `make setup` (user decision: keep for evaluators; risk documented) |
| Overrides | **Append-only** `score_decisions` (kind `override` \| `accept`). The newest row counts. Edits add a row, so earlier HR reasons are kept |
| Score columns | On `scoring_jobs`: `suggested_score`, `suggested_reason`, `needs_person_reason`, `model`, `finished_at`. Added by **this plan's autogenerated migration** as nullable columns. The candidate migration `7e042563977a` stays untouched. Alembic autogenerate can't add CHECKs to an existing table, so the invariants (score 1–4; `scored` has score + reason; `queued`/`running`/`failed` have no score; `needs_person` has a reason) are enforced by SQLAlchemy `@validates`/`before_flush` on `ScoringJob` plus tests. The DB-level gap is documented in architecture.md |
| Extras in scope | Jobs list + status filter; HR-only audio playback; accept suggested score |
| Double-click | Override/accept: an identical repeat of the newest decision → 200 with the same row. `UNIQUE(answer_id, sequence)` catches concurrent inserts. Retry: conditional `UPDATE … WHERE status='failed'`; a repeat while queued → 200 no-op |
| Final score | Newest decision's score, else `suggested_score` when job is `scored`, else `null`. `needs_person` has no final score until HR overrides. `failed` never has a score (ORM invariant + read-side gate `visible_suggestion`). `avg_suggested` counts `scored` only. A candidate resubmission starts a fresh final score; earlier decisions stay visible under `earlier_submissions` |

| Method | Path | Success | Errors |
|---|---|---|---|
| POST | `/api/hr/session` | 200 | 401, 415, 422, 503 |

| GET | `/api/hr/roles` | 200 | 401 |

| GET | `/api/hr/jobs` | 200 | 401, 422 |
| GET | `/api/hr/answers/{answer_id}/audio` | 200, 206 (audio bytes) | 401, 404, 416 |
| POST | `/api/hr/answers/{answer_id}/override` | 201, 200 | 401, 404, 409, 415, 422 |

The 9 routes guarded by `get_current_hr` are all of the above except `POST` and `DELETE /api/hr/session`. The route-table test asserts exactly this set.

## Acceptance criteria
- [ ] Sign-in with `.env` creds → 200 + httpOnly cookie; wrong creds → 401; creds unset → 503; non-JSON body → 415; sign-out → old cookie 401; changing `HR_PASSWORD`/`HR_EMAIL` → old cookie 401
- [ ] Every guarded `/api/hr/*` route (9) depends on `get_current_hr` and returns 401 with no cookie **and** with a valid candidate Bearer token (route-table test via the recursive `tests/route_table.py` helper)
- [ ] Candidate endpoints with only an HR cookie → 401
- [ ] Candidate review shows per question: current answer (text or audio meta), earlier submissions with `superseded_at` and their decisions, job status/attempts/last error, visible suggested score + reason, needs-person reason, decisions newest first, final score + source
- [ ] Failed job → `suggested_score` and `final_score` null, excluded from averages, **even when the DB row holds a score** (raw-SQL test); the ORM refuses to flush a failed job that has a score
- [ ] All API timestamps carry a UTC offset (`Z`/`+00:00`), HR and candidate
- [ ] Override needs score 1–4 + non-blank reason; identical repeat → 200, no new row; override on superseded answer → 409, including when the supersede races the request
- [ ] Accept only on a `scored` job whose suggestion matches the posted score; `needs_person` → 409 (override required); otherwise 409
- [ ] Retry: failed → queued (attempts 0, error cleared); repeat → 200 no-op, including a concurrent double click; other statuses → 409
- [ ] Jobs list filters by status, excludes `superseded` by default, returns counts per status
- [ ] Audio streams to HR with a content type chosen from the file extension (never the stored upload header), `nosniff` + CSP sandbox, Range → 206; non-audio answer → 404; path can't leave the resolved `UPLOAD_DIR`
- [ ] `docs/api-doc.md` HR sections meet the same checklist as the candidate sections; HR doc-coverage tests check status codes per table row and exact `detail` strings
- [ ] `api-types.ts`, `docs/architecture.md`, README (HR sign-in, MOCK label, `.env` creds) updated
- [ ] `make lint && make test` green; `uv run alembic check` clean

## Out of scope
LLM scoring worker + prompt-injection handling (next plan; it writes the score columns) · all frontend pages · "Read first" ordering · HR-score agreement report · "Load data pack" button (use `make seed`) · multiple HR users / roles · rate limiting on sign-in · CSRF tokens (JSON content-type + no CORS instead; see Decisions) · tightening the candidate upload content-type allow-list (the HR audio route ignores the stored type).
